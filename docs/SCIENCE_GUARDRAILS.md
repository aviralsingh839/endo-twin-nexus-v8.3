# ENDO-TWIN Scientific & Safety Guardrails

## Purpose

ENDO-TWIN is a research and engineering platform for longitudinal physiological modelling. CHRONO-PCOS is a disease-specific research module inside the platform.

The software must never turn a prototype signal, symptom, image feature, or model output into a clinical diagnosis.

## Provenance is mandatory

Every observation or result should carry one provenance state:

- MEASURED — directly acquired from a sensor/device.
- DERIVED — mathematically computed from measured data.
- CLINICALLY_ENTERED — supplied by an authorized human/clinical workflow.
- IMAGE-DERIVED — extracted from an imported image after an explicit image-analysis step.
- MODEL-INFERRED — generated by a model from supported inputs.
- DEMO_DATA — synthetic, illustrative, or showcase data.
- UNKNOWN — origin or validity cannot be established reliably.

Do not silently convert one provenance class into another.

## Data quality

Quality is separate from provenance.

A low-quality measured value is still measured; it should not become a fabricated value simply to fill a chart. Long missing intervals remain missing. Bounded interpolation must be explicit and quality-penalized.

Downstream models should receive channel-level quality context where supported.

## Personal baseline

Interpret longitudinal change against the individual's own baseline only when enough valid observations exist.

A baseline confidence value describes statistical/data support for the baseline. It is not medical certainty.

## Model outputs

Every model result should expose:

- model name and version
- input features and provenance
- dataset/version where applicable
- validation strategy
- training/validation date where applicable
- data-quality context
- model uncertainty/confidence
- limitations
- clinical-validation status

Never describe a research probability as a diagnosis.

## Ultrasound guardrail

An ultrasound pipeline may be:

IMPORT → VALIDATE → PREPROCESS → ANALYZE → EXTRACT FEATURES → MODEL → UNCERTAINTY → REPORT

However, anatomical features such as cyst count, cyst size, ovarian volume, or morphology must remain UNKNOWN unless the software has actual evidence supporting those computed features.

Do not invent accuracy, confidence, training performance, or anatomical findings.

For supervised image evaluation, split at the patient level rather than mixing images from the same patient across train and test sets.

## Demo boundary

Demo screens must visibly say DEMO_DATA or equivalent.

A synthetic patient, illustrative distance, sample sensor value, example ultrasound result, or example model score must never look like a live clinical record.

## Privacy

The default architecture is local-first and offline-capable.

Patient-scoped records must use stable identifiers and patient-scoped queries. A doctor workspace must switch the entire data context when a patient is selected; records from another patient must not leak into the selected workspace.

## Scientific language

Prefer wording such as:

- research signal
- illustrative example
- model-inferred
- data quality
- unknown
- clinical validation not established

Avoid:

- diagnoses PCOS
- 100% accurate
- clinically proven unless independently established for the exact model and setting
- fabricated training/validation metrics
- unsupported causal claims
